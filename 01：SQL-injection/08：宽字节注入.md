# 宽字节注入

## 一、环境

- 靶场：自建本地 sqli-labs-master 靶场
- 工具：Burp Suite + HackBar
- 数据库：MySQL
- 编码环境：GBK 等宽字节编码

## 二、什么是宽字节注入

宽字节注入主要出现在：

**数据库使用 GBK 等宽字节编码，而程序又使用 `addslashes()` 等方式对输入进行转义时。**

正常情况下：

```sql
'
```

可能被转义成：

```text
\'
```

这样单引号就不能正常闭合。

宽字节注入利用的是：

**某些字节与 `\` 组合后，会被 GBK 当成一个中文字符，从而让原本的反斜杠失去转义作用。**

于是原本被转义的：

```text
\'
```

可能重新变成一个可以参与 SQL 解析的：

```text
'
```

从而绕过转义。

## 三、基本原理

正常情况：

```text
输入 '
 ↓
addslashes()
 ↓
\'
 ↓
单引号被转义
 ↓
无法闭合
```

宽字节环境：

```text
输入 %df'
 ↓
程序转义
 ↓
%df\'
 ↓
GBK 解析
 ↓
%df\ 被识别为一个宽字节字符
 ↓
剩下的 ' 重新成为单引号
 ↓
形成注入
```

所以核心就是：

**利用编码解析差异吃掉反斜杠 `\`。**

## 四、常见 Payload

经典测试：

```sql
%df'
```

然后根据实际 SQL 结构继续构造注入。

例如常见形式：

```sql
%df' or 1=1--+
```

其中 `%df` 是常见的测试字节,也可在81-FF 中任意选取。

不过具体使用哪个字节，要根据**服务器、PHP、数据库和字符集环境**判断，并不是所有环境都一定使用 `%df`。

## 五、为什么 `%df` 有效

这里最重要的是理解：

```text
%df + \
```

在某些 GBK 环境下，可以组成一个合法的双字节字符。

原本：

```text
%df\'
```

经过解析后可能变成：

```text
[一个宽字节字符] + '
```

于是：

```text
\
```

不再单独承担转义作用。

最后单引号：

```text
'
```

重新获得了 SQL 语法意义。

## 六、判断思路

可以先观察正常输入：

```sql
'
```

如果发现单引号被转义，无法正常注入，再考虑是否存在宽字节环境。

然后测试：

```sql
%df'
```

观察页面响应是否发生变化。

如果原本：

```text
'
```

不能闭合，

而：

```text
%df'
```

可以产生不同的 SQL 行为，

就可以进一步判断是否存在宽字节注入。

## 七、和普通 SQL 注入的区别

### 普通 SQL 注入

直接利用：

```text
'
```

闭合原来的 SQL：

```text
' + 注入语句
```

### 宽字节注入

因为：

```text
'
```

被转义：

```text
\'
```

所以利用编码解析：

```text
%df + \
```

让反斜杠被宽字节“吃掉”，重新释放：

```text
'
```

所以可以理解成：

**普通注入解决的是 SQL 语法问题，宽字节注入首先解决的是“转义字符把单引号保护起来”的问题。**

## 八、我的理解

宽字节注入的核心并不是 `%df` 本身。

真正需要理解的是：

```text
程序处理输入
      ↓
添加反斜杠进行转义
      ↓
数据库按照 GBK 解析
      ↓
反斜杠与前一个字节组成宽字符
      ↓
反斜杠失去原本的转义作用
      ↓
单引号重新参与 SQL 解析
```

所以它本质上是：

**程序的字符编码处理方式与数据库解析方式不一致，导致转义被绕过。**

## 九、关键知识点

```text
宽字节注入
├── 常见环境：GBK
├── addslashes()
├── 反斜杠 \
├── 宽字节字符
├── %df
└── 编码解析差异
```

核心记忆：

**宽字节注入 = 利用 GBK 等宽字节编码的解析差异，使转义产生的 `\` 失效，从而让单引号重新参与 SQL 解析。**
