# 服务端请求伪造 SSRF

## 1. 实验环境

- 靶场：自建本地 CMS 靶场（PHP + MySQL + Apache）
- 工具：BP（Burp Suite）+ HackBar
- 漏洞类型：服务端请求伪造（SSRF）

## 2. 什么是 SSRF

SSRF：

> Server-Side Request Forgery，服务端请求伪造。

简单理解：

> **本来应该由用户访问的地址，却变成了服务器帮用户发起请求。**

例如程序存在：

```
?url=http://example.com
```

后端可能类似：

```
$url = $_GET['url'];
$content = file_get_contents($url);
```

这时候用户可以控制服务器请求的目标地址，就可能产生 SSRF。

## 3. 基本思路

我测试 SSRF 时，主要关注：

```
找到可以控制 URL 的参数
        ↓
正常访问一个外部地址
        ↓
修改请求目标
        ↓
尝试访问服务器自身
        ↓
判断服务器是否真的发起了请求
```

常见参数：

```
url=
uri=
target=
redirect=
path=
link=
src=
```

参数名字不重要，关键是后端是否会根据用户输入发起网络请求。

## 4. SSRF 和普通请求的区别

正常情况：

```
用户 → 目标服务器
```

SSRF：

```
用户 → 目标服务器
          ↓
       服务器再请求
          ↓
       另一个目标
```

所以 SSRF 的核心就是：

> **让服务器替我访问我原本无法直接访问的目标。**

## 5. 测试本机服务

如果服务器存在 SSRF，可以尝试让服务器请求自己的地址：

```
http://127.0.0.1/
```

或者：

```
http://localhost/
```

也可以根据实际环境测试：

```
http://127.0.0.1:80/
http://127.0.0.1:8080/
```

如果服务器能够正常返回内部服务的内容，说明请求确实是由服务器发出的。

## 6. SSRF 常见危害

### ① 访问内网服务

服务器可能可以访问：

```
127.0.0.1
localhost
内网 IP
```

而外部攻击者本身无法直接访问这些地址。

### ② 访问内部管理页面

例如：

```
http://127.0.0.1/admin
```

如果内部管理页面只允许本机访问，就可能被 SSRF 间接访问。

### ③ 云环境中的元数据服务

部分云环境存在内部元数据服务。

如果服务器可以访问相关地址，SSRF 可能进一步造成敏感信息泄露。

因此实际测试云服务器时，需要特别关注：

> **服务器能访问什么内部资源。**

## 7. SSRF 和 CSRF 的区别

这两个名字比较容易混淆。

### CSRF

```
攻击者 → 借助受害者浏览器 → 请求目标网站
```

重点：

> **利用用户的身份发起请求。**

### SSRF

```
攻击者 → 目标服务器 → 请求其他服务器
```

重点：

> **利用服务器的网络权限发起请求。**

简单记：

```
CSRF：利用用户

SSRF：利用服务器
```

## 8. SSRF 测试重点

发现类似：

```
url=
target=
redirect=
link=
src=
```

这类参数时，可以重点考虑：

```
是否可以控制 URL
        ↓
服务器是否会主动请求
        ↓
能否访问 localhost
        ↓
能否访问内网地址
        ↓
能否访问内部服务
```

## 9. 当前学习理解

我现在对 SSRF 的理解：

> **SSRF 的核心不是“伪造一个请求”这么简单，而是利用服务器本身的网络访问能力，让服务器替我访问目标。**

所以判断 SSRF 时最重要的是：

```
用户可控 URL
      +
服务器主动发起请求
      =
可能存在 SSRF
```

      ↓
